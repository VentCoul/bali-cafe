# Design Spec: CRM, Loyalty & Auth System Integration

**Date:** 2026-08-18  
**Topic:** Створення бази клієнтів, інтеграція системи лояльності та розширеної авторизації  

## 1. Мета
Перетворити базовий додаток для онлайн-замовлень на повноцінну клієнтоорієнтовану платформу, яка дозволить:
- Реєструвати клієнтів (Email + Пароль / Google Auth).
- Накопичувати та використовувати бонуси за допомогою існуючої системи лояльності Poster.
- Створювати персоналізований досвід: збереження "Улюблених" страв, історія замовлень, швидке повторення попередніх покупок.

## 2. Технологічний стек (Найсучасніший стандарт для Next.js 14+)
- **База Даних:** PostgreSQL (рекомендований хостинг Vercel Postgres, Neon або Supabase). Це гарантує надійність та швидкість.
- **ORM:** Prisma. Найсучасніший та найбезпечніший інструмент для роботи з базою даних у екосистемі Node.js/Next.js. Гарантує сувору типізацію та автоматичні міграції.
- **Авторизація:** Auth.js (NextAuth v5). Стандарт індустрії для безпечної обробки сесій та OAuth провайдерів (Google) з вбудованим захистом від CSRF/XSS.
- **Валідація:** Zod. Використовуватиметься для валідації вхідних даних при реєстрації/авторизації.

## 3. Структура Бази Даних (Prisma Schema)

```prisma
model User {
  id               String    @id @default(cuid())
  name             String?
  email            String?   @unique
  passwordHash     String?   // Для тих, хто обрав класичну реєстрацію
  phone            String?   @unique // Обов'язкове поле для зв'язку з Poster
  posterClientId   String?   // ID клієнта в Poster
  image            String?   // Аватарка з Google
  role             Role      @default(USER)
  createdAt        DateTime  @default(now())
  
  accounts         Account[] // NextAuth зв'язки (Google)
  sessions         Session[] // NextAuth сесії
  favorites        Favorite[]
  orders           Order[]
}

model Favorite {
  id        String   @id @default(cuid())
  userId    String
  productId String   // ID товару в Poster
  user      User     @relation(fields: [userId], references: [id])
  createdAt DateTime @default(now())

  @@unique([userId, productId])
}

model Order {
  id             String   @id @default(cuid())
  userId         String?
  posterOrderId  String?  // ID транзакції в Poster
  totalAmount    Float
  bonusUsed      Float    @default(0) // Скільки бонусів списано
  bonusAccrued   Float    @default(0) // Скільки бонусів нараховано
  status         String   // NEW, PAID, COMPLETED
  pickupTime     String?  // На яку годину (або "найближчий час")
  createdAt      DateTime @default(now())

  user           User?    @relation(fields: [userId], references: [id])
}
```

## 4. Користувацькі флоу (User Flows)

### 4.1. Ролі та Адмін-доступ
Зараз адмін-панель захищена загальним паролем з `.env`. Після міграції на базу даних ми перейдемо до рольової моделі:
- В базі створюється перелік ролей: `enum Role { USER, ADMIN }`.
- Користувачі з роллю `ADMIN` матимуть ексклюзивний доступ до всіх сторінок `/admin/*` (Налаштування меню, конфігурація тощо).
- **Перший адміністратор:** Може бути призначений вручну через пряму зміну в базі даних або за допомогою скрипта ініціалізації (seed), або існуючий пароль з `.env` буде використовуватись для "Super Admin" входу, який дозволить призначати права `ADMIN` іншим зареєстрованим користувачам.

### 4.2. Авторизація
1. Користувач натискає "Увійти".
2. Бачить модалку/сторінку з двома опціями: "Увійти через Google" та форма "Email + Пароль".
3. **Якщо Google:** Auth.js автоматично створює User (якщо немає) і заповнює `name`, `email`. Після логіну перевіряємо, чи заповнене поле `phone`. Якщо ні — показуємо обов'язкове вікно: "Введіть номер телефону для нарахування бонусів".
4. **Якщо Email/Пароль:** Класична форма реєстрації, де телефон є обов'язковим з самого початку.

### 4.3. Синхронізація з Poster (Головна логіка бонусів)
Ми **не** зберігаємо баланс бонусів у нашій БД на постійній основі (щоб уникнути розсинхронізації з офлайн-касою). Poster є єдиним "джерелом правди".
- Після того як юзер ввів телефон, ми робимо запит до `clients.getClients` в Poster API.
- Якщо такий клієнт вже є: беремо його `client_id` з Poster і зберігаємо в `User.posterClientId`.
- Якщо немає: робимо `clients.createClient`, створюємо його в Poster, і зберігаємо новий `client_id`.
- При відкритті "Особистого кабінету" або "Корзини", ми в реальному часі робимо GET-запит до Poster API, щоб показати актуальну суму накопичених бонусів.

### 4.4. Оформлення замовлення (Самовивіз)
- При чекауті авторизований клієнт бачить чекбокс: "Списати бонуси (Доступно: X грн)".
- Якщо він обирає списати бонуси, ми передаємо цю інформацію в Poster при створенні замовлення (`incomingOrders.createIncomingOrder`).
- Клієнт обирає час: "На найближчий час" або "На точну годину" (зі списку доступних інтервалів).

## 5. Безпека
- Паролі хешуються через `bcryptjs` або `argon2`.
- Всі API ендпоінти, що стосуються користувача, будуть захищені перевіркою сесії.
- Доступ до Poster API здійснюється виключно з серверних (Server Actions / Route Handlers) компонентів Next.js. Клієнт не матиме прямого доступу до токенів Poster.

## 6. Наступні кроки для реалізації
Після затвердження цієї специфікації ми:
1. Ініціалізуємо Prisma та налаштуємо PostgreSQL.
2. Встановимо та налаштуємо Auth.js.
3. Створимо UI для логіну/реєстрації.
4. Додамо логіку синхронізації телефонів з Poster.
5. Розробимо сторінку "Особистий кабінет" з історією та бонусами.
6. Оновимо чекаут для підтримки бонусів та вибору часу самовивозу.
