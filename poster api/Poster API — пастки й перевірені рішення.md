# Poster API — пастки й перевірені рішення

> Місця, де офіційна документація мовчить, бреше або суперечить сама собі. Кожен пункт коштував реального часу щонайменше в одному проекті — часто в двох, бо знахідка не була записана.

## 1. `storage.createWriteOff` — недокументований формат тіла

Офіційний приклад вводить в оману. Правильна структура: `ingredient` лежить **на верхньому рівні**, поруч із `write_off`, а не всередині нього. Усі значення — **рядки**. Кількість — це `weight`, а не `amount`.

```json
{
  "write_off": { "storage_id": "1", "date": "2026-07-26 10:00:00", "reason_id": "3" },
  "ingredient": [
    { "id": "1933", "type": "4", "weight": "0.5", "reason": "Telegram: Оля" }
  ]
}
```

- `reason` всередині позиції — це **вільний коментар**, який видно в кабінеті Poster. Не плутати з `reason_id` у `write_off` (довідник причин).
- Успіх — `{"success": 1, "response": <writeoff_id>}`. Перевіряти саме `success`, не наявність `response`.

> **Двічі спіймано:** у `poster-client` (Mobile Hub) цей payload був плаский — `{storage_id, products}`. Виявилось лише 2026-07-15, звірянням з точним прикладом у доках. Write-off Bot наступив на ті самі граблі в травні.

## 2. Чотири різні enum'и `type` — і вони не сумісні

Найдорожча пастка в усій екосистемі. Слово `type` означає різне в кожному контексті, і значення **перетинаються числами**:

| Контекст | 1 | 2 | 3 | 4 | 5 | інше |
|---|---|---|---|---|---|---|
| `storage.createWriteOff` → `ingredient[].type` | товар | тех.карта | напівфабрикат | інгредієнт | модифікатор | |
| `menu.getProducts` → `type` | — | тех.карта (`ingredient_id=0`) | товар (є `ingredient_id`) | | | |
| `group_modifications[].modifications[].type` | товар | тех.карта | напівфабрикат | | | 8 — модифікація товару, 10 — інгредієнт, 0 — без списання |
| `Leftover.ingredients_type` | *своя система кодів* | | | | | |

**Правило конверсії `getProducts` → `createWriteOff`:**

```python
writeoff_type = "2" if get_products_type == "2" else "1"   # страва → 2, решта → товар(1)
```

Якщо передати `getProducts type=3` напряму, Poster трактує товар як напівфабрикат і відповідає **помилкою 32** («prepack_id is undefined»). Перевірено на живому акаунті: товар списується коректно як `type=1` за `product_id`.

## 3. Одиниця виміру береться з `weight_flag`, а не з поля `unit`

У тех.карти поле `unit` — це «kg», бо такою є основа її калькуляції, хоча продається й списується вона порційно.

- `weight_flag = 0` → штучний товар → **шт**
- `weight_flag = 1` → ваговий → **кг / л** (тоді дивитись на `unit`)

Симптом ігнорування: «Капучино 250 мл» показується в кілограмах.

Коди одиниць інгредієнта (`ingredient_unit`): `kg` — кілограми, `l` — літри, `p` — штуки.

## 4. `product_id` та `ingredient_id` — різні простори ID, що перетинаються

Один і той самий номер може означати два різні об'єкти. Реальний приклад із акаунту `sirny`: **2066** — це водночас інгредієнт «Ожина» і товар «Пиво Cerdos Voladores Pale Ale».

Наслідок: будь-який словник/кеш, ключований лише по ID, тихо з'їдає половину каталогу — позиції зникають з пошуку без жодної помилки. Ключ має бути **складений**: `(item_type, id)`.

## 5. Методів, яких не існує (хоч їх логічно очікувати)

| Викликаєш | Що буде | Правильний метод |
|---|---|---|
| `storage.getWriteOffReasons` | код 30, «Method Not Allowed» | **`storage.getWasteReasons`** |
| `storage.getWriteOffs` | не існує | **`storage.getWastes`** |
| `menu.getModificators` | **HTTP 405** | групові модифікатори приходять вкладеними в `menu.getProducts` (`group_modifications[]`) |

> `menu.getModificators` роками висів у Write-off Bot і мовчки падав у `return_exceptions=True` — тобто гілка модифікаторів у каталозі ніколи не наповнювалась. Перевірено 2026-07-26 на обох акаунтах: 405.

У `getWasteReasons` кожна причина — `{"reason_id": 1, "name": "порча", "pnl_group": 3, "delete": 0}`. М'яко видалені (`delete != 0`) треба відфільтровувати самому.

## 6. Відповідь буває і списком, і словником

`storage.getStorageLeftovers` та деякі інші методи інколи повертають `{storage_id: [...]}` замість плаского списку — залежить від акаунту й параметрів. Парсер має вміти обидва варіанти, інакше «раптово порожній каталог» на іншому клієнті:

```python
if isinstance(response, dict):
    response = [x for v in response.values() if isinstance(v, list) for x in v]
```

## 7. Назви товарів містять лапки — і це ламає fuzzy-пошук

Poster-акаунти масово оформлюють назви як `Пиво "Золотий ель" непастеризоване, нефільтроване 0,33л`, `Вода "Карпатська джерельна" 1л`, `Пиво «Гіннес» банка 0.44л`.

Якщо в `rapidfuzz` передати `processor=str.lower`, лапки й коми **залишаються приклеєними до токенів**: `"золотий`, `ель"`. Перетин множин токенів із чистим запитом користувача — порожній, і `token_set_ratio` деградує до порівняння короткого запиту з 55-символьним рядком.

Виміряно на каталозі `sirny` (1584 позиції):

| Запит → «Пиво "Золотий ель"…» | Скор | Поріг 55 |
|---|---|---|
| `processor=str.lower` | **27** | не проходить |
| `processor=utils.default_process` | **100** | 1-ше місце |

**Рішення:** завжди `rapidfuzz.utils.default_process` — він замінює всі не-літерно-цифрові символи пробілами, після чого токенізація працює як задумано. Ціна — жодної, якість решти пошуку не падає.

## 8. OAuth: два різні `redirect_uri` в одному флоу

- Poster **не повертає** параметр `state`. Свій ідентифікатор (щоб знати, який саме адмін почав авторизацію) треба вбудовувати **в сам `redirect_uri`** — його Poster віддає назад дослівно, дописуючи свої `code` та `account`.
- Але на кроці обміну коду `redirect_uri` має бути **точно таким, як зареєстровано в налаштуваннях застосунку** — без жодних query-параметрів. Інакше «Redirect URI does not match registered redirect URI».
- Обмін коду йде на **піддомен акаунту**: `https://{account}.joinposter.com/api/v2/auth/access_token`, параметри — `client_id` / `client_secret` (не `application_id` / `application_secret`, як у крокові авторизації).
- Токен живе 2 роки.

## 9. Читання списань ≠ ручні списання

`storage.getWastes` змішує ручні списання з можливими авто-списаннями за тех.картами — Poster ніде не документує, які саме записи туди потрапляють. Для розрахунку **реального споживання** надійніше рахувати з продажів: `dash.getTransactions(include_products=True)` → тех.карта через `menu.getProduct` для `type=2`, пряма конверсія г/мл → кг/л для `type=3`.

## Швидкий чекліст для нової інтеграції

- [ ] `type` мапиться між контекстами, а не передається наскрізь
- [ ] Одиниця береться з `weight_flag`
- [ ] Кеш/словники ключовані парою `(type, id)`
- [ ] Парсер відповіді витримує і `list`, і `dict`
- [ ] Fuzzy-пошук на `default_process`
- [ ] Перевірено, що метод узагалі існує (405/30 ловляться мовчки в `try`)
